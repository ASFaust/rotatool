# Design note: the Ledger generate / edit / regenerate model

> This supersedes plan.md's "materialize then generate" description. It was
> originally a working-session memory; copied into the repo so it's available
> on any machine.

Andreas rejected the plan.md "materialize then generate" split for the Ledger.
**Reason:** only `strict` shifts have a fixed occurrence; for
`strictTime`/`anyTime`, *which* day/time the shift happens is itself a solver
decision, so they can't be materialized before solving. The materialize button
was removed in Phase 3.

## The model (implemented in Phase 4)

- A single **Generate** over a date range produces a full solution — concrete
  `LedgerShift`s *and* `LedgerAssignment`s, all status `autogenerated`. The
  solver chooses window-group days/times.
- **Auto-lock on any manual edit:** touching an autogenerated shift or
  assignment promotes it to `committed`. (Granularity is the whole shift:
  editing one assignment promotes the entire shift + all its assignments.)
- **Regenerate** holds `committed`/`performed` fixed and recomputes the rest:
  drop autogenerated shifts/assignments in range, treat committed/performed
  people as busy (no double-book), skip shifts coinciding with a committed one
  (no duplicates), re-run.
- `status` (`autogenerated|committed|performed`) lives on **LedgerShifts** as
  well as assignments (a shift's existence/timing is a solver output). There's a
  `status` column in the LedgerShifts sheet + schema.
- Ad-hoc hand-added shifts are user-created → committed from birth.

**Where:** solver in `src/solver/` (builder/highs-adapter/worker/solve/
formulation/generate). `generateRoster(range)` → the Generate button in
`LedgerView`. `applyGeneration` does the clear/keep/write. `busyIntervals`
prevents double-booking. `expandAll` in `expand.ts` feeds the solver.

## v1 deviations / known refinements (to do in a later pass)

1. **Auto-lock granularity is the whole shift**, not the individual seat.
   Per-seat locking needs seat-assignment vars.
2. **Committed shifts aren't refilled by regenerate** (the plan's "pre-assign,
   then solver fills remaining seats" / ledger-fixed seat filling is deferred).
3. **Coverage double-counts multi-attribute people** — one person can satisfy
   several requirements at once. Exact fix = per-(instance,requirement) seat vars.
4. Soft coverage was chosen over hard `>= count` (graceful degradation).
